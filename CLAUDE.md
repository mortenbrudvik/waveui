# CLAUDE.md — waveui

## What is this?

`@mortenbrudvik/waveui` (the npm name since 0.4.0; the repository's `package.json` said `waveui` before 0.5): a React 19 component library of 80 components inspired by the Fluent UI 2 design language, built with TypeScript, Tailwind CSS 4 and `--wave-*` CSS custom properties, with light, dark and high-contrast themes and RTL support. It is **not** Microsoft's `@fluentui/react-components`.

User docs: `README.md` (install, styles, theming, customization, RSC, keyboard), `CHANGELOG.md`, `docs/WAVE-UI-GUIDE.md` (design and development guide), `docs/testing-best-practices.md` (how to test here), `docs/UPGRADING-TO-1.0.md` (every change 1.0 made, with the old and the new form; its tables restate the 0.18 inventory `src/lib/deprecations.ts`, retired in 1.0). The 0.5 design and every convention below come from `docs/superpowers/specs/2026-09-23-review-fixes-design.md` (§1 lists the C-* conventions in full). Fluent UI v9 parity: `docs/ROADMAP.md` (the plan from 0.6 to 1.0, one phase per minor release; its gap ids come from `docs/research/fluent-ui-v9-comparison.md`) and the 0.6 design, `docs/superpowers/specs/2026-09-25-fluent-parity-phase-1-design.md` (its design rulings, and implementation notes where the code deliberately deviates; Storybook MCP: `npm run dev` also serves Storybook's MCP server at `http://localhost:6006/mcp` (`@storybook/addon-mcp` with `features.componentsManifest`), registered for Claude Code in `.mcp.json`; Claude Code asks once before it uses a project server. `docs-list`, `docs-show` and `docs-show-story` show a component as autodocs and an app's agent see it; `stories-preview` returns story URLs. The server's instructions say to answer component questions from those tools and never from source: that fits apps that use WaveUI, not this repository, where the source, its JSDoc and this file decide. Limits: the manifest lacks the export JSDoc of compounds (autodocs gets it from `.storybook/exportDocblocks.ts`), and `stories-find-by-component` maps a component to every story, because the stories import `../src`.

`prepublishOnly` runs typecheck, build, `verify-dist --final`, tests, `check:package` and `test:pack`. Do not hard-code test counts anywhere.

Toolchain: `devEngines` requires Node `^22.22.2 || ^24.15.0 || >=26.0.0` (npm stops on another) and npm >= 11.11 (warns; older npm drops the lockfile's `libc` fields). The package's own floor is `engines.node` `>=22.12.0` (the first Node.js whose `require()` loads the ES-only package unflagged), and `check-ts-coverage` requires the `@types/node` major to equal it. `allowScripts` denies the install scripts of esbuild and @parcel/watcher (prebuilt binaries); npm 12 blocks every other dependency install script until approved (`npm install-scripts ls`).

## Architecture

- `src/components/<category>/` — `button`, `input`, `data-display`, `typography`, `layout`, `navigation`, `feedback`, `overlays`, `table`, `provider` (WaveProvider; its context value, `WaveContextValue`, holds `theme`, `dir`, `themeClassName`, `portalContainer`, `inputDefaults`, `motion`, `hasProvider` and, since 0.17, `tokens` (the merged overrides, as given), `tokenStyle` (their inline style, `undefined` when empty) and `applyStylesToPortals`; the provider merges `tokens` with `mergeTokenOverrides`, keeps the merged map's identity through a previous-value state while its entries are equal, collects the style with `collectTokenStyle` during render and reports the skipped entries from an effect), `motion` (public `Presence`). Plus `portal/` (public `Portal`, the only place that copies the provider's theme classes, direction and, unless `applyStylesToPortals` is `false`, `tokenStyle` onto an overlay: its wrapper's `style` spreads the overrides before its own `position` and `z-index`) and `internal/` (`HiddenInput`, never exported). Component-private helpers sit next to their component with a prefixed name (`buttonStyles.ts`, `Button.semantics.ts` (`useButtonSemantics`: role, tab stop, Enter/Space activation and disabled/`disabledFocusable` handling shared by Button and Link), `Button.slots.tsx` (how other components' slots treat a `<button>`/`Button`: `BUTTON_OWN_PROP_KEYS`, `placeButtonIcon`, `MERGED_DISABLED_FOCUSABLE_PROPS`, `mergedAriaDisabledClasses` for the dismiss/clear merge of MessageBar, SearchBox and Tag; `unwrapButtonGlyph` for the glyph slots of SplitButton, MenuButton, `PickerExpandButton`, Dropdown's `expandIcon` and the swatch `icon`s, and since 1.0 for a Tag `dismissIcon` object whose `as` is a button (MessageBar's and SearchBox's `dismiss` unwrap one through `resolveWiredSlot`); `withPartClass` for a variant's icon class on Button's own icon span (ToggleButton, CompoundButton, MenuButton, SplitButton and the Toolbar buttons; `Toolbar.parts.tsx`'s `withIconBox` is built on it)), `Badge.colors.ts` (the color map shared by Badge and CounterBadge), `tagStyles.ts` (the metrics and looks of Tag, InteractionTag and TagPicker's tags; `tagRootClasses`), `TagGroup.context.ts` (the TagGroup context, the module-only host seams `TagGroupHostContext` and `TagHostContext` of TagPicker, the tag item hook with focus after a removal, the held focus of a control disabled while focused (`useHeldFocus`) and the Delete/Backspace test (`isDismissKey`); since 0.18 `TAG_PART_LOCKS` and `BLOCK_CLICK`, the locks and the click block of the tag family's parts, and the host member `dismissButtonPart`, which takes TagPicker's `removeButton` part to a default tag's Dismiss button; imports no component), `InteractionTag.tsx`, `Avatar.context.ts` (`AvatarSizeContext`: the box size in pixels and the shape that a tag or an AvatarGroup gives its Avatar; `AvatarBadgeSizeContext`: the size a PresenceBadge in an Avatar takes), `Avatar.sizes.ts` (`AvatarSize`, `AvatarNumericSize`, the box and text class maps, `avatarPixelSize`, `avatarBadgeSize`), `Avatar.colors.ts` (`AvatarColor`, the named-color classes, `resolveAvatarColor` and the FNV-1a hash behind `colorful`), `colorUtils.ts`, `dateUtils.ts` (the date and time helpers of DatePicker, Calendar and TimePicker: parsing, formatting, the grids and ranges, the time options, and since 1.0 `localeTimeFormat`, the hour cycle of a language, which a TimePicker without `format` reads once per picker in the browser, never on the server or in the hydrating render; built on `src/lib/date.ts`; also the public type `CalendarSelectionRange`), `Option.tsx` (`Option`, `OptionGroup`, and the public `ListboxProvider`, `ListboxSurface` (with `listProps`) and `useListboxPopup` of custom pickers), `input/pickerLabels.ts` (the English defaults of the pickers' `labels`, the multi-select toggle announcements, `PickerAnnouncer`), `input/pickerValues.ts` (multi-select value arrays: normalising, toggling, a reset compared by content), `List.registry.ts`, `MessageBar.status.tsx`, `Dialog.shared.tsx` (also `useModalOpenState`/`requestOpen`, the dismiss-reason mapping of Dialog and Drawer, the trigger toggle with `popup` (`false`: no `aria-haspopup`, an inline drawer's trigger), `useModalOpener` (the non-modal opener), `useRaiseOnOpen` and `useOpenInsideWarning`), `Dialog.slots.tsx` (`ModalCloseButton`, `ModalBackdrop`, `useBackdropAppearance`: the `closeButton` and `backdrop` slots of Dialog, Drawer and NavDrawer), `Popover.shared.tsx` (`PopoverBeak`, `usePopoverTabOrder`, `isFocusInSurfaceTree`, shared by Popover, TeachingPopover and InfoButton), `input/pickerPresence.ts` (`usePickerSurfacePresence`: the presence of a picker's popup surface, what it held when it was last shown and whether its list may exit; `ListboxSurface` and TimePicker use it), `input/pickerStyles.ts` (`PICKER_ICON_BUTTON_CLASSES`, and per size `pickerIconButtonClasses`, `pickerButtonOffset`, `pickerEndPadding(buttons, size)`, `pickerGlyphSize`), `input/inputLook.ts` (`useInputLook`: the size and appearance a text control or picker renders), `input/fieldLabel.ts` (`markFieldLabel`/`isFieldLabelElement`: the marker by which Field recognizes a `Label` or `InfoLabel` element passed as `label`, without importing them), `input/RadioGroup.context.ts` (0.18: `RadioGroupContext` with its full value `RadioGroupItemsContextValue`, `useRadioItemState`, the item state that `RadioGroup.Item` and `useRadioGroupItem` share, and the public `useRadioGroupContext` and `useRadioGroupItem`; imports no component), `input/Rating.item.tsx` (`RatingItem`, the rating context and the star glyphs shared by Rating and RatingDisplay; both are compounds with `Item`), `data-display/InfoButton.tsx` (the standalone info button with its portaled note, built on the overlay hooks and `Popover.shared`; InfoLabel uses it), `input/Combobox.expand.tsx` (`PickerExpandButton`, shared by Combobox, TimePicker and TagPicker despite its name, with `dimDisabled`; `showsExpandButton`, which Dropdown also imports), `input/Combobox.text.ts` (`insertedText`, `replacedText`: the text an edit of the multi-select Combobox's labels inserted), `input/routedHandlers.ts`, `table/useGridNavigation.ts`, `button/Toolbar.parts.tsx` and `button/Toolbar.context.ts` (the Toolbar parts and their context), `button/Toolbar.navigation.ts` (`TOOLBAR_ITEM_SELECTOR`, `useToolbarNavigation`: the arrow-axis rule of Toolbar and TagGroup), `MessageBar.parts.tsx` (`MessageBar.Title`, `MessageBar.Actions` and the context that marks them placed), `MessageBar.reflow.ts` (`useMessageBarReflow`; ## Conventions (every component, hook and story)

The conventions gate (`src/__tests__/conventions.test.ts`) enforces the mechanical ones with one test per source file of `src/components` and for `src/lib/motion.ts` (raw colours also in `stories/`); the rest of `src/hooks` and `src/lib` (including the `src/lib/styles.ts` recipes) is review-only, as is everything else.

- **C-REF** — `ref` is declared in the Props interface (`ref?: React.Ref<HTMLButtonElement>`), React 19 ref-as-prop; no `forwardRef`. Every component and sub-component sets `displayName`. **Where `ref` goes (1.0, Phase 14 spec R5, superseding the Phase 13 spec's R19):** on a form control whose root wraps one focusable element, `ref` reaches that element, and the root, which keeps `className`, `style` and the rest props, is the `root` part (`slotProps.root`, its `ref` included): Input, Checkbox, Switch, `RadioGroup.Item`, SearchBox, SpinButton, ColorSlider, AlphaSlider, `ColorPicker.HexField`, Combobox, Dropdown, TimePicker, DatePicker and TagPicker (`Ref<HTMLInputElement | HTMLButtonElement>`, the trigger that renders), the fourteen of `SLOT_PROPS_ROOT_OWNERS`. The component merges `ref` into the control's own merged ref (Checkbox: `useMergedRefs(buttonRef, ref, slotProps?.indicator?.ref)`, the place 0.x's `controlRef` held), so an inline `ref` never detaches the component's own or a positioning reference; a root that holds a ref of the component (a picker's dismiss reference) merges `slotProps.root.ref` beside it, set after the spread (C-COMPOSE). `controlRef` is left only on ColorArea (two inputs, one Tab stop), `Table.SelectionCell` and `DataGrid.SelectionCell`; every other component's `ref`, groups and collections included, reaches its root. A new wrapper control follows the rule and joins `SLOT_PROPS_ROOT_OWNERS`; test it with `testSystemProps({ ref: 'control', control })` and `testRootPartRef` (Testing).
- **C-COMPOSE** — destructure every handler the component also uses and compose it: `onClick={composeEventHandlers(onClick, internal)}` (consumer first; `preventDefault()` skips ours). `className` via `wcn(internal, className)` (user last: it replaces conflicting classes of the same variant, the user's unprefixed `p-2` included against Wave's `wave:p-4`; see Styling), `style` merged, refs with `useMergedRefs`, id lists with `joinIds`, props objects with `mergeProps`. Defaults consumers may override (`type="button"`, `role`) go **before** `{...rest}`; attributes that must win (disabled `tabIndex={-1}`) go **after**. A handler that reacts to events bubbling through the React tree (click, focus, pointer, key) ignores events whose target is not inside `event.currentTarget` in the DOM (portal bubbling from a Popover, Menu or Dialog opened inside it). Three exceptions count events from a portal opened inside them on purpose: the Toaster's region-wide pause handlers (focus and pointer: a menu opened from a toast keeps every timer paused), the focus handlers of a Tree row's actions toolbar (focus in a surface opened from an action holds the actions shown, so its focus return can reach the action), and the focus and blur handlers of a windowed List and a FlatTree (0.16: focus moving into a popup an item opened keeps that item rendered and its index kept until focus leaves both, decided in a microtask); their key handlers, and the Toaster's activation handlers, keep the rule. **Parts (0.18):** a part's element spreads `mergeSlotProps(slotProps?.<part>, { className, style, ref, defaults, locked, blockHandlers })` (`src/lib/slotProps.ts`): `defaults`, then the consumer's props, then `locked`; `className` is `wcn(<stable class>, <component classes>, part.className)` (the component's string untouched without a consumer class), `style` the part's keys over `own.style`, the ref merged (cached per pair of refs), `aria-labelledby`/`aria-describedby` (`ID_LIST_KEYS`) joined with the component's ids first; a consumer handler (only a function counts) runs first and its `preventDefault()` skips the component's handler of that key; `null`/`undefined` from the consumer removes nothing; `children`, `as`, `key` and `dangerouslySetInnerHTML` are type errors and dropped; `className`, `style` and `ref` go in `own`, never in `defaults` or `locked`, and a handler in one of the two, never both. **Locked** is the attribute object the component writes on the element (`className`, `style` and `ref` aside), its own props routed to the part included (so they win over `slotProps`; Fluent's consumer props win), and its handler of the part (its own prop composed with the internal one, cancellable by the part's `preventDefault()`). A locked key wins even when `undefined`, but only a key present in `locked` overwrites: an attribute that a hook or helper spread adds only while it is set (`aria-activedescendant`, `data-selected`, `aria-current`, the `inert`/`hidden` of a presence phase, a roving `tabIndex`) needs an explicit `undefined` lock before that spread, and a "state off" test. Lock unset, besides: `hidden`, `inert` and `aria-hidden` on a part that holds a control, an item or a name (`HIDDEN_PART_LOCKS`); `role`, `tabIndex`, `data-roving-container` (and `data-roving-disabled`, `data-roving-value`, `aria-disabled` and the family's markers where the part could become an item) on a part inside a roving container, a toolbar or a grid (`ROVING_PART_LOCKS` holds the six); `aria-label` on a part whose text names a control; `tabIndex` on a decorative part; the Field wiring through `fieldLocks` on a control part, `name`/`form` on the focusable part of a control whose value a `HiddenInput` submits, and `defaultValue` beside a locked `value`; a positioned surface's position, size limits and visibility through `lockPositionStyle`; the presence attributes on a presence surface. A `root` part of 1.0 (C-REF; Input's, of 0.18, keeps its rules) locks the root's enumerated `data-*` attributes, then the component's own root props (its `...rest`, after the data attributes as in 0.18), then `hidden`, `inert` and `aria-hidden` at the component's own values (ruling BF; `RadioGroup.Item`, whose rest props reach the radio, locks them unset); a `<label>` root (Checkbox, Switch, `RadioGroup.Item`, `ColorPicker.HexField`) also locks `htmlFor` unset, before the component's own root props; only a root whose click activates the control (the label roots of Checkbox, Switch and `RadioGroup.Item`) passes `blockHandlers` while it is unavailable (ruling BG). Must-run bookkeeping (a handler that only mirrors focus, pointer capture, a drag's end, a held key or the pointer's place into state) is composed after the spread with `checkDefaultPrevented: false` (`composeAfterPart(slotProps?.x?.onFocus, ours)` where the part's handler is read from `slotProps` itself), and the part's JSDoc says so. A part inside a control that does not activate while disabled (the control's own `disabled`, `disabledFocusable` or an unavailable focusable state, never a consumer `aria-disabled` alone) passes `blockHandlers` (a module constant, `BLOCK_CLICK`) so the consumer's `onClick` is not called. `own.ref` is a callback ref (a `useMergedRefs` result or a state setter: `react-hooks/refs` rejects a ref object passed to a function during render); a part whose element holds a ref of the component sets `ref={useMergedRefs(localRef, slotProps?.x?.ref)}` after the spread, so an inline consumer ref never detaches the component's, and a function that reads a ref and goes through the merge becomes a `useEventCallback`. A repeated part (per item, row, cell or toast) merges only when given, `{...(part && mergeSlotProps(part, own))}` after the plain attributes, with no hook or memo object per item; a part that feeds a memoised context or item asks for a stable object in its JSDoc. Without `slotProps` (or with `{}`) every part renders the attribute set and values of before, only their order may differ (ruling AA), and nothing behaves differently (ruling AL: a new `defaultPrevented` check is gated on the part being given).
- **C-CLASS** — expose state as `data-*` attributes (`data-selected`, `data-active`, `data-disabled`, `data-state`) and style with `data-[selected]:…`, so consumers can target it. Enumerated attributes are always rendered with the resolved value, the default included (`data-orientation="vertical"`, `data-appearance="primary"`, `data-color="brand"`, `data-label-position="after"`, `data-validation-state="none"`, `data-modal-type="modal"`, `data-state="shown"`, `data-type="overlay"`, `data-scroll-state="none"`, `data-appearance="dimmed"`, `data-focus-mode="tab"`, `data-overflow="wrap"`), so a `[data-orientation=vertical]` selector always works; boolean ones are present (`""`) or absent (`data-dot`, `data-compact`, `data-contains-current`, `data-disabled-focusable`, `data-separator`, `data-collapsed`, `data-create`). They go before `{...rest}`, as Stepper's `data-orientation` does; the `data-state` of a presence surface (Popover.Content, the TeachingPopover surface, `Menu.Popover`) goes after it on purpose, since the surface's own state must win. `data-presence` is enumerated (always rendered with its phase). Toggle state: `aria-pressed` only on buttons; a toggle with a checked role uses `aria-checked` and `data-checked`, so one `data-[checked]:` selector matches every checked item of a `checkedValues` group (menu items, toolbar radios); ToggleButton always adds `data-pressed` while pressed. Every public component and part carries its stable class from `src/lib/classNames.ts` (`wave-<name>`, `wave-<name>__<part>`), first in its `wcn()`, on the element that receives `className`, written as a literal member access (`buttonClassNames.root`); variants carry their base classes (a variant's icon through `withPartClass`), and a nested public component its parent's part class; no state classes; the registry and the `data-*` attributes are under semver, so no class or attribute is removed or renamed in a 1.x minor (1.0 removed `wave-tag-picker__control` and `wave-tag-picker__group`). The stable classes carry no utility prefix: they are the registry's names, not Tailwind utilities. A new component or part registers its constant in the same change, and places each part key of it in `src/lib/slotParts.ts` (C-SLOTS); the conventions gate (`class-names`), `testSystemProps` and the completeness gate enforce it. Text controls and pickers (Input, Textarea, Select, SearchBox, SpinButton, Combobox, Dropdown, DatePicker, TimePicker, TagPicker) take `size?: CoreSize` and `appearance?: InputAppearance`, draw them with the maps of `src/lib/styles.ts` (`inputHeightClasses`, `inputTextClasses`, `inputPaddingClasses`, `inputAppearanceClasses`; compose `inputFocus`/`inputInvalid` after them) and resolve them with `useInputLook`: the control's own prop, then the surrounding Field's `size`, then `WaveProvider inputDefaults`, then `medium`/`outline` (a size outside the control's `sizes` is skipped; TagPicker has no `small`). `data-size` and `data-appearance` are enumerated attributes on the element that receives `className`; Checkbox, Switch and Slider render `data-size` (Checkbox also `data-shape`), Rating, RatingDisplay `data-color`, InfoButton `data-size`, and Field `data-size`. Tag, TagGroup and InteractionTag render `data-size`, `data-appearance` and `data-shape` (TagGroup also `data-orientation`); Dialog.Content `data-size`; the Drawer panel `data-type`, `data-position`, `data-size` and, overlay, `data-modal-type`; backdrops `data-appearance`; NavDrawer.Body `data-focus-mode`; drawer headers, bodies and footers `data-scroll-state`. Avatar renders `data-size`, `data-shape`, `data-color` and `data-active`/`data-active-appearance`; AvatarGroup `data-layout`; PresenceBadge `data-status`; TabList `data-appearance`, `data-size` and `data-orientation`; Card `data-appearance`, `data-size` and `data-orientation`; Carousel `data-appearance` and `data-controls-layout` on the root and a boolean `data-dragging` on the track; `Carousel.Button` `data-direction`. Overflow renders `data-orientation`, `data-overflow-direction` and `data-button-position`; Breadcrumb `data-size`, `data-focus-mode` and `data-overflow`; DataGrid `data-selection-appearance` and a boolean `data-subtle-selection` on the table; `Table.SelectionCell` `data-type`, `Table.CellLayout` `data-appearance` (only while set: the prop has no default) and a boolean `data-truncate`, `Table.CellActions` a boolean `data-visible`; the sort glyphs `data-direction`; List `data-navigation-mode` (the resolved mode) and a boolean `data-checkmark`, `List.Item` a boolean `data-disabled-selection`; the TeachingPopover surface and `TeachingPopover.Footer` `data-layout`, `TeachingPopover.CarouselFooter` `data-carousel-layout` (its own `layout`, never `data-layout`). MessageBarGroup renders `data-animate`, Carousel `data-motion` (`slide`, `fade`, `none`), and Popover.Content, the Tooltip surface and the TeachingPopover surface `data-state` (`open`, `closed` while they exit) next to `data-presence`. The 0.15 elements carry their part classes: the collapse elements (`accordionPanelClassNames.collapse`, `treeItemClassNames.collapse`, `navCategoryClassNames.collapse`, `drawerClassNames.collapse`, with `navDrawerClassNames.collapse` on an inline NavDrawer's), `messageBarGroupClassNames.item` and `toasterClassNames.toastContent`. Windowing and resizing (0.16): every spacer of a window carries a boolean `data-virtual-spacer` and its component's `spacer` key (`dataGridClassNames.spacer`, `listClassNames.spacer`, `listboxClassNames.spacer`, `comboboxClassNames.spacer`, `dropdownClassNames.spacer`, `flatTreeClassNames.spacer`); a windowed DataGrid's body rows carry `data-row-index` (the 0-based sorted position, which `useGridNavigation`'s `model` reads) after `{...rest}`, a windowed List's items and every FlatTree item `data-index`; a DataGrid carries a boolean `data-resizing` while a handle drags, and `Table.ResizeHandle` `data-dragging` while dragged and `data-grid-auxiliary`, the boolean that makes a widget auxiliary to `useGridNavigation` (never a cell's target, so a sortable header's sort button keeps Enter; F2 on the cell or its target widget moves focus to it, and Tab moves between them in interaction mode). FlatTree renders `data-selection-mode` and its items boolean `data-selected`, `data-current`, `data-checked`, `data-mixed` and `data-disabled`. New constants: `flatTreeClassNames` (`root`, `spacer`), `flatTreeItemClassNames` (`root`, `row`, `expandIcon`, `indicator`, `label`), `tableResizeHandleClassNames`, and `dataGridHeaderCellClassNames.resizeHandle` on a DataGrid's handle next to its own class.
- **C-TOKENS** — only theme tokens: no `[#hex]`, `rgb()`, `white`/`black` or palette utilities, no `var(--grey-*)`. **The utility prefix (1.0, Phase 14 spec R6):** every utility the library writes in `src/components` and `src/lib` carries Tailwind's prefix `wave:` (`wave:flex`, `wave:bg-primary`, `wave:text-body-1`, `wave:shadow-4`, `wave:wave-rtl:-scale-x-100`, the group markers `wave:group/row`), written against the internal unnamespaced theme of `src/styles/theme.css`; the namespaced keys (`bg-wave-primary`) are an app's, never the library's. The compile check of `scripts/build-css.mjs` fails a class word without the prefix (Styling). Hover/pressed styles of anything that can be disabled use the literal gate `wave:not-disabled:not-aria-disabled:hover:` / `…:active:`; the `enabled:` variant is banned (it never matches `<a>`/role=button); the conventions gate reads these rules alike with and without the prefix. Only runtime user colors (swatches) may be raw, marked `// wave-allow-color: <reason>`; stories mark fixture data `// wave-allow-color: fixture`. Stories write classes as an app does (unprefixed, with the namespaced token keys: `bg-wave-primary`, `text-wave-body-1`), compiled by `.storybook/stories.css`. Since 1.0 only the `--wave-*` names exist: `tokens.css` neither reads nor declares a 0.4 name (`--brand-N`, `--grey-N`, the 0.4 semantic names), and the theme classes are `wave-light`, `wave-dark` and `wave-high-contrast` alone. Theming (0.17) has two routes, and components support both by reading tokens only: the inline-style route (`WaveProvider tokens`, `getTokenStyle`: `--wave-*` custom properties in the `style` of the provider root, rendered on the server too, and of every portal wrapper, in the client (Portal renders nothing on the server); never a `<style>` element or a nonce, so under a `style-src` without `'unsafe-inline'` the server-rendered overrides do not apply, and such an app ships a stylesheet and passes no `tokens`) and the stylesheet route (the ramps and other theme-independent tokens on `:root`, the semantic tokens under the theme selectors). Only WaveProvider and Portal write token overrides, and no component reads a token's value in JavaScript (a canvas chart does that, in the chart stories). Shadows are per-theme tokens (`--wave-shadow-N` in every theme group; `@theme inline` maps `--shadow-N` to them), so `shadow-N` follows the theme, and a shadow color utility or opacity modifier no longer reaches it. The persona palette has five roles per hue: `palette-<hue>` (the strong fill, 3:1 on `background`, a chart series), `-foreground` (text on the fill), `-tint` (a surface), `-tint-foreground` (text and icons on the tint, the page and cards) and `-border` (the hue's stroke, declared as `var()` of the fill); no component uses the tints yet, and `./styles` ships only the palette utilities components use.
- **C-RADIUS** — Tailwind's default radius names (`rounded`, `rounded-md`, …); no theme overrides.
- **C-LOGICAL** — logical utilities (`ms/me/ps/pe`, `start-*/end-*`, `border-s/e`, `rounded-s/e`, `text-start/end`); mirror with Wave's `wave-rtl:` variant (by the element's own `:dir(rtl)`, compiled as `:nth-child(n of :dir(rtl))`, which CSS minifiers keep): write the LTR value as the base class and override it (`wave:wave-rtl:-scale-x-100` on directional glyphs; `translate-x-*` needs a `wave-rtl:` counterpart). Tailwind's bare `rtl:`/`ltr:` (and `not-rtl:`/`not-ltr:`) fail the gate (`direction-variant`) and the CSS build; horizontal arrow keys go through `getArrowIntent(key, { orientation, dir: getDirection(el) })`. A physical utility needs `// wave-allow-physical: <reason>`. Directional components get an RTL test (`renderWithProviders(ui, { dir: 'rtl' })`).
- **C-FOCUS** — `focusRing` on focusable controls, `focusRingInset` on cells/rows, `inputFocus`/`inputFocusWithin` on text inputs (inner control `focus:outline-hidden`). Never `focus:outline-none` and never bare `outline-hidden` (it draws a permanent outline in forced colors).
- **C-MOTION** — every `transition*`/`animate-*` class string carries a `motion-reduce:` variant of the same kind, or the line carries `// wave-allow-motion: <reason>`; animations use `animate-wave-*`. There is no global reduced-motion reset. Every overlay and disclosure mounts through `usePresence` (`data-presence` phases; the exiting element is `inert`; every top-level element of a portal carries the presence attributes; `appear: true` for a surface gated on hydration, `open && isClient`, never for in-flow content), including, since 1.1, the listbox popups of Combobox, Dropdown, TagPicker and TimePicker (`ListboxSurface`, with `input/pickerPresence.ts`: the one `<ul role="listbox">` stays in the surface while it exits, held as it was last shown, and a list whose items changed as it closed, or the empty message, unmounts at once), the DatePicker calendar and the AvatarGroup popover, each with a `motion` slot on `popupMotion`; layers, the trap, isolation, scroll lock, focus restore and positioning key on the open state, not on the mount, and focus leaves a closing surface in the closing commit (`useModalLayer`; `useFocusBeforeClose` for positioned popups, with `useRestoreFocus`'s targets in its order; the trigger for a disclosure). Since 0.15 components ship their motion from `src/lib/motion.ts` only: one plain string literal per recipe value, every class with the prefix `wave:` (no concatenation, template or `wcn()` there; components compose at run time), described in words in its JSDoc and never as a class; `data-[presence=…]` classes appear in no other source file (`presence-class`), every `starting:` is gated as `wave:data-[presence=entering]:starting:` (`starting-gate`: `@starting-style` also applies to an element that mounts `entered`, `appear={false}` or hydration), and the gate scans `src/lib/motion.ts` with every rule but `class-names` and `presence-class`. Recipes time with `duration-wave-*`/`ease-wave-*` (the tokens are never zeroed) and pass `src/lib/__tests__/motion.test.ts` (every class compiles; tokens; a `motion-reduce:` counterpart on the same element; positioned surfaces list their properties explicitly, never `transform`, which floating-ui places them with; a backdrop ends with its surface; grid structures pin both tracks at a zero minimum and align their part); a new recipe raises `MOTION_RECIPE_MIN` in `scripts/verify-dist.mjs`, whose Button-only probe proves no motion module, recipe or presence class there (Button imports neither `lib/motion` nor `hooks/useMotion`). A part takes its motion as a slot (C-NAMING), destructures it, resolves it with `useMotionClasses(slot, recipe)` (`undefined` the recipe, `null` none, a value replaces it; `WaveProvider motion="none"` acts as `null` unless a value is given; a consumer's motion value is written as an app writes classes, unprefixed) and composes `wcn(<stable class>, <base>, <motion classes>, className)`. A `className` with presence variants is a plain class list composed after the motion classes (1.0 removed the 0.14 rule by which it turned the default off on `Menu.Popover`, `Dialog.Content`, Drawer and NavDrawer), so a class of the same variant replaces only the recipe's conflicting `wave:` word. A disclosure's part collapses in a collapse element (`useCollapsePresence`; inline drawers and MessageBarGroup bars have their own structures): the presence element around the part, `display: contents` while entered, a clipping one-track `minmax(0, …)` grid while it moves, its other track pinned and its part aligned to the edge it slides from. Positioned popups render `data-state` and `data-side`.
- **C-DISABLED** — a control that disables itself through its own activation (Pagination/Carousel boundary buttons, TeachingPopover Back) uses `focusableDisabledProps(disabled)` (`aria-disabled` + `data-disabled`) and guards its handlers; roving containers skip it. `disabledFocusable` (button family, Link, Switch, Checkbox) renders `focusableDisabledProps(true, { reachable: true })` (`aria-disabled`, `data-disabled`, `data-disabled-focusable`) instead of the native `disabled`, stays in the tab order, prevents activation (click, Enter, Space, implicit submission) without calling the consumer's handler and stops the click from reaching ancestors (as a natively disabled control), wins over `disabled`, and stays in roving containers' arrow order (`useRovingTabIndex` keeps `data-disabled-focusable` items unless natively disabled or `data-roving-disabled`). Button and Link get it from `Button.semantics.ts`. A consumer `aria-disabled` without `disabledFocusable` keeps its 0.5 meaning (the look only; handlers run), except that `Menu.Trigger` ignores activation from an `aria-disabled="true"` element. The dimmed look of a focusable disabled control lifts while its ring shows, because `opacity` also dims the outline: `wave:aria-disabled:focus-visible:opacity-100` (in `disabledStyles`, `buttonDisabledClasses`, Link and the merged dismiss/clear buttons), and `wave:has-focus-visible:opacity-100` on the dimmed root of Checkbox, Switch, `RadioGroup.Item`, SearchBox and Input (with slots), which lifts for any focus ring inside it. A tag control disabled while it has focus (Tag's Dismiss button, InteractionTag's buttons, TagPicker's remove and clear buttons) keeps it: `MERGED_DISABLED_FOCUSABLE_PROPS` (the attributes of `focusableDisabledProps(true, { reachable: true })`, `disabled: false` and a blocked click) until it loses focus, then the native `disabled`. A field that dims as a whole (TagPicker's control) keeps the controls inside it from dimming again while it dims (`dimDisabled={!disabled}` of `PickerExpandButton` and of TagGroup's host options). ### Field wiring for a custom control

```tsx
import * as React from 'react';
import { wcn } from '../../lib/cn';
import { composeEventHandlers } from '../../lib/composeEventHandlers';
import { mergeSlotProps, type SlotPart } from '../../lib/slotProps';
import { focusRing } from '../../lib/styles';
import { useControllable } from '../../hooks/useControllable';
import { useFieldContext, useFieldControl } from '../../hooks/useFieldControl';
import { useFormReset } from '../../hooks/useFormReset';
import { useMergedRefs } from '../../hooks/useMergedRefs';
import { HiddenInput } from '../internal/HiddenInput';

export interface ToggleProps extends Omit<React.HTMLAttributes<HTMLSpanElement>, 'onClick'> {
  checked?: boolean;
  defaultChecked?: boolean;
  onCheckedChange?: (checked: boolean) => void;
  name?: string;
  form?: string;
  required?: boolean;
  onClick?: React.MouseEventHandler<HTMLButtonElement>;
  /** The `role="switch"` button: `ref` reaches the focusable element (C-REF). */
  ref?: React.Ref<HTMLButtonElement>;
  /** `root`: the wrapper, which takes `className`, `style` and the rest props. */
  slotProps?: { root?: SlotPart<'span'> };
}

export const Toggle = ({
  checked: checkedProp,
  defaultChecked = false,
  onCheckedChange,
  name,
  form,
  required,
  id,
  'aria-label': ariaLabel,
  'aria-labelledby': ariaLabelledBy,
  'aria-describedby': ariaDescribedBy,
  onClick,
  className,
  style,
  ref,
  slotProps,
  ...rest
}: ToggleProps) => {
  const [checked, setChecked] = useControllable(checkedProp, defaultChecked, onCheckedChange);
  // Label, validation message, hint, invalid and required state from the surrounding Field
  // (C-ROUTING).
  const fieldProps = useFieldControl({
    id,
    'aria-label': ariaLabel,
    'aria-labelledby': ariaLabelledBy,
    'aria-describedby': ariaDescribedBy,
    'aria-required': required,
  });
  const field = useFieldContext();
  const buttonRef = React.useRef<HTMLButtonElement>(null);
  const mergedButtonRef = useMergedRefs(buttonRef, ref);
  useFormReset(buttonRef, () => setChecked(defaultChecked), form);
  // The wrapper is the root part (C-COMPOSE): the part's classes, style and handlers merge after
  // the component's, and the component's own root props and hidden state win over the part's.
  // A library component also puts its stable class first and joins SLOT_PROPS_ROOT_OWNERS.
  const rootProps = mergeSlotProps(slotProps?.root, {
    className: wcn('wave:relative wave:inline-flex', className),
    style,
    locked: { ...rest, hidden: rest.hidden, inert: rest.inert, 'aria-hidden': rest['aria-hidden'] },
  });

  return (
    <span {...rootProps}>
      <button
        type="button"
        {...fieldProps}
        ref={mergedButtonRef}
        role="switch"
        aria-checked={checked}
        data-checked={checked ? '' : undefined}
        className={wcn(
          'wave:rounded-md wave:border wave:border-stroke-accessible wave:px-3 wave:data-[checked]:bg-selected',
          focusRing,
        )}
        onClick={composeEventHandlers(onClick, () => setChecked((prev) => !prev))}
      />
      <HiddenInput
        type="checkbox"
        name={name}
        form={form}
        checked={checked}
        value="on"
        required={required ?? field?.required ?? false}
        onInvalid={() => buttonRef.current?.focus()}
      />
    </span>
  );
};
Toggle.displayName = 'Toggle';
```

- `useFieldControl(props, { labelable, nativeRequired })` returns only defined keys: the consumer's id, else the Field's `controlId` (only the first control of a Field takes it); `aria-labelledby` pointing at the Field label when `<label htmlFor>` cannot reach the control (`labelable: false` for `role="radiogroup"`/`role="group"` roots, or a control that is not Field's first child); `aria-describedby` joined with the Field's validation message (`validationMessageId ?? errorId`) and then its hint; `aria-invalid`/`aria-required` from the Field; `required` only with `nativeRequired: true` (native inputs: Input, Select, Textarea, Slider, SpinButton, SearchBox).
- `FieldContextValue` (0.6): `validationState` (`'none' | 'error' | 'warning' | 'success'`) and `validationMessageId` (the message's id in every state) are optional, absent in contexts built before 0.6 (read the state as `invalid ? 'error' : 'none'`). Only the error state sets `invalid` (so `aria-invalid`); `errorId` is set only in the error state, and `hasErrorMessage` only in the error state with a message: a control that shows its own error (Input `error`, DatePicker and TimePicker rejected text) hides it only then, so its error still shows next to a Field warning. A control that builds `aria-describedby` itself (ColorPicker's hex input) uses `field?.validationMessageId ?? (invalid ? field?.errorId : undefined)`; one that reads the Field state for a look (ProgressBar's fill) uses `validationState`.
- `HiddenInput` renders nothing without `name` or `required`. Pass `required ?? field?.required`, so a required Field makes the control natively required even without `name` (the CHANGELOG documents this); an explicit `required={false}` wins, for `aria-required` too. Use `type="radio"` for single-choice groups, `"checkbox"` for booleans, `"text"` for free values (pickers, SpinButton), and pass arrays for multi-value controls (one input per value).
- Test Field consumption without the real Field through `renderWithFieldContext` (`src/test-utils-field.tsx`; `{ validationState: 'warning', validationMessageId: FIELD_TEST_IDS.messageId }` for a warning). The real Field around another component's control belongs in `src/__tests__/integration.test.tsx`. `renderWithFieldContext(ui, { size })` sets the Field's size; `renderWithProviders(ui, { inputDefaults })` sets `WaveProvider inputDefaults`. Resolution-order tests of a text control cover its own prop, the Field size, the provider default and the fallback, each winning over the next.

## Styling

- Tokens are `--wave-*` variables in `src/styles/tokens.css` (`:root`/`.wave-light`, `.wave-dark`, `.wave-high-contrast`; 1.0 removed `.dark` and `.high-contrast`), mapped twice in `@theme inline`: for the library by the internal `src/styles/theme.css` (`--color-primary: var(--wave-primary)`, written `wave:bg-primary` in a component), for apps by the namespaced keys of `tokens.css` (`--color-wave-primary`, used as `bg-wave-primary`); a parity test keeps the two one to one. Every theme group declares every token; `color-scheme` only on theme classes. The library's sheets: `dist/styles.css` (`./styles`, unlayered, for apps without Tailwind), `dist/components.css` (the same utilities without the token and base rules, internal, which `./tailwind` layers as `@layer theme, base, components, utilities`), `dist/utilities.css` (`./utilities`, the namespaced token utilities, unlayered, linked after `./styles`).
- Never use raw hex values or palette colors in components or stories; the conventions gate fails on them. Contrast pairs are listed in `src/styles/__tests__/tokensHarness.ts` (`CONTRAST_PAIRS`, the text matrix, `NOT_TEXT_TOKENS`) and asserted by `tokens.test.ts` in all three themes: add a new token's values to `TOKENS` in `tokens.test.ts` and its pairs and classification to the harness (docs/testing-best-practices.md, "Tokens: the contrast matrix and brand seeds"). A new color token also gets its internal key in `theme.css`, its namespaced key in `tokens.css` and its name in `WAVE_TOKEN_NAMES`, and the codemod's `THEME_TABLE` is regenerated (`node codemod/migrate-1.0.mjs --print-table src/styles/tokens.css`); a test fails until each follows.
- `wcn()` (module-only; the public `cn` is the same merge, ruling BK) is clsx + tailwind-merge with Wave's prefix, extended with Wave's scales under both names: a class and its `wave:` twin are one utility, so a user's `p-2` replaces Wave's `wave:p-4`, `wcn('wave:text-body-1', 'text-wave-foreground')` keeps both (a ramp step is a font size), and the last class wins for real conflicts (`wcn('wave:shadow-4', 'shadow-wave-8')` → `shadow-wave-8`). A user class replaces only a conflicting class **of the same variant**. The gated hover/pressed classes (`wave:not-disabled:not-aria-disabled:hover:` / `…:active:`) and the `data-[…]:`/`aria-*:` state classes are kept next to a bare user class and, with `./styles`, win by specificity (`wcn('… wave:not-disabled:not-aria-disabled:hover:bg-primary-hover', 'hover:bg-wave-error')` keeps both; the gated (0,4,0) beats `:hover` (0,2,0)). Consumers override them with the same variant chain (`not-disabled:not-aria-disabled:hover:bg-wave-error`, which replaces the gated class), the important modifier (`hover:bg-wave-error!`) or the same data variant; with `./tailwind` any utility of the app wins over Wave's `components` layer anyway. `Button.test.tsx` pins this pitfall. A `tw:` class of a prefixed app is kept next to Wave's (its layer decides).
- In an app without Tailwind a Tailwind class passed in `className` still replaces Wave's conflicting class through the merge but has no CSS (`./styles` defines only `wave:` classes); the README says so, and `./utilities` gives such apps the token utilities only.
- 4px spacing grid; type ramp `text-caption-2` … `text-display`; shadows `shadow-2` … `shadow-64` (per-theme tokens since 0.17; the library writes them `wave:text-body-1`, `wave:shadow-4`, an app `text-wave-body-1`, `shadow-wave-4`); fonts `font-wave`, `font-wave-mono` and `font-wave-numeric`; weights `regular`, `medium`, `semibold` and `bold` (`TextWeight`); motion `duration-wave-ultra-fast` … `duration-wave-ultra-slow` and `ease-wave-*` (Fluent's motion tokens: `--wave-duration-*`/`--wave-curve-*` on `:root`, theme-independent).
- **Words in `src/components` and `src/lib` (1.0).** The library sheet compiles with `prefix(wave)`, so Tailwind generates a class only from a word that carries `wave:`: an unprefixed utility name in a comment or a non-class string generates nothing (the `@source not inline()` list of 0.x is gone), and a JSDoc example may name an app's classes (`bg-wave-primary`). What the build checks instead (docs/WAVE-UI-GUIDE.md Pattern 5): (1) the compile check, the first step of `scripts/build-css.mjs` (`scripts/prefix-codemod.mjs --check --class-free src/hooks src/components src/lib src/hooks`), reads the words of every string literal through the TypeScript AST, never a comment: a literal the class-context tracing reaches (`wcn`, `cn` and `clsx` arguments, `className=`, recipe and `*Classes` maps, `withPartClass`, `src/lib/styles.ts`, `src/lib/motion.ts`) may hold no unprefixed utility word at all, nor a prefixed word that compiles to nothing (the prefix after a variant or a `!`, `hover:wave:bg-primary`, or an unknown utility, `wave:bg-primry`), and any other literal (a role `grid`, a positioning strategy `fixed`, a prop value `outline`, an event name `blur`) may hold one only where `scripts/prefix-allowlist.json` names that word for that file (read the place, then add the pair; a pair is a decision); (2) a `wave:` class that a comment names but no class string uses ships a class no component draws, and the stray-class assertion fails the build: name it in words, or without the prefix. `src/lib/motion.ts` describes its recipes in words; the guide's "Component Motion" section and the README hold the class strings. `src/hooks`, which the CSS build does not scan, holds no class string (`useCollapsePresence` merges the recipes of `lib/motion` with `wcn`): the compile check fails a prefixed word in any of its string literals, and its unprefixed utility words go through the allowlist like the others.
- Named Tailwind groups belong to one family each, so a component nested in another's cell never reacts to the outer row: Tree's rows are `wave:group/row`, Nav's `wave:group/nav-row`, Table and DataGrid rows `wave:group/table-row`, and a DataGrid with `subtleSelection` is `wave:group/grid` (the markers carry the prefix since 1.0, so an app's `group-hover/table-row:` matches nothing: an app reveals against a group of its own); a new reveal picks a name of its own (docs/WAVE-UI-GUIDE.md Pattern 18). `Table.Cell` and `DataGrid.Cell` are `relative`, the box of `Table.CellActions`.
- The stable classes (`wave-button`, `wave-button__icon`, from `src/lib/classNames.ts`) are hooks for consumers, under semver since 1.0: the library never styles through them and Tailwind generates nothing for them. The registry is under `src/lib`, so its JSDoc follows the word rule above (name elements by role, "the grid element").

- Menu item kinds are tested through `renderInMenuList` (`{ dir: 'rtl' }` for RTL; or `MenuListHarness`, for `renderToString` and a controlled parent) from `navigation/__tests__/menuHarness.tsx`: the Menu and list contexts without the root, trigger and popover modules. `onCheckedValuesChange` tests assert the values and `details` (`{ name, checkedItems, event }`), once per change in StrictMode.
- Active-descendant widgets (Listbox, the listbox pickers, composites on `useActiveDescendant`): DOM focus stays on the combobox or the list; assert its `aria-activedescendant`, resolved to the option through `document.getElementById`, and the option's `data-active`, never focus on an option (docs/testing-best-practices.md §5). To assert scrolling, spy with `vi.spyOn(Element.prototype, 'scrollIntoView')` in a suite that calls `vi.restoreAllMocks()` after each test (the component tests), or replace the method with a spy and put the original back in `finally` (the hook tests).
- Dates (Calendar, DatePicker): `vi.setSystemTime(NOW)` in a `beforeEach` (undone by `vi.useRealTimers()` in the `afterEach`), `locale="en-US"`, and a fixed `today` where the case is about today; compare dates by their local fields (each suite's `fields(date)` helper), so the suites pass in every time zone.
- `onTestFinished` callbacks run after `src/test-setup.ts`'s body check: a test that appends its own container (`renderToString` + `hydrateRoot`) removes it in `try`/`finally` or an `afterEach`. With a modal Dialog open, query elements behind it with `{ hidden: true }`.
- Production-mode checks stub `NODE_ENV` with `vi.stubEnv` (a module mock of `isDev` does not reach `reportMissingContext`; docs/testing-best-practices.md §8).
- Pending lists keep the gates green while a phase's parallel packages land: `PENDING_FLAT_EXPORTS` (`scripts/verify-dist.mjs`; `--final` requires it empty), `PENDING_CLASS_NAMES` (`src/__tests__/classNames.test.ts`), `PENDING_PUBLIC_TYPES` (`src/__tests__/public-types.test.ts`), `PENDING_FLAT_MEMBERS` (the barrel test of `src/__tests__/integration.test.tsx`) and, since 0.18, `PENDING_SLOT_PARTS` (`src/lib/slotParts.ts`: part keys not yet placed; `slotParts.test.ts` requires it empty once a phase is integrated). The package that adds a compound member, a class-name constant, a part key or a public type fills them; INTEGRATION empties them.
- Tags, drawers and the app shell: backdrops are the surface's siblings (query them by their constant, never through `parentElement`); TagGroup's focus after a removal is asserted after a microtask, and a held key is `fireEvent.keyDown(el, { key: 'Delete', repeat: true })`; TagPicker removals: a pointer click has `detail > 0`, a keyboard one `detail: 0`; count mode is measured with `installResizeObserverMock` and stubbed widths; drawer scroll state: stub `scrollHeight`/`clientHeight`/`scrollTop` and `fireEvent.scroll` in `act`; kept-mounted surfaces: `{ hidden: true }` while closed and no `autoFocus` inside; Nav lists: render only parts or `<li>` there; an arrow-key NavDrawer body: assert the stamps after mount, never in the server HTML; responsive app shells: `mockMatchMedia({ '(max-width: 767px)': true })` (`NavDrawer.appShell.test.tsx` composes the AppShell story).
- Cross-component compositions (Menu + MenuButton, Field around every control, Toast over Dialog, …) live in `src/__tests__/integration.test.tsx`, together with the Server Component regression suite (add every new compound there; docs/testing-best-practices.md §5).

## Claude Code setup

`.claude/settings.json` wires two hooks and turns the `vercel` and `frontend-design` plugins off in this repository. Both hooks run `scripts/claude/hooks.mjs` with the tools of the checkout that holds the edited file, so an edit in a worktree uses that worktree's `node_modules`; `$CLAUDE_PROJECT_DIR` stays on the main checkout inside a worktree, so a change to the hook script takes effect once it is on main.

- **After an edit** (PostToolUse on Edit/Write): Prettier formats the file when `npm run format` covers it and ESLint lints it when `npm run lint` does (both read from package.json). Errors go back to Claude (exit code 2), warnings as context. Files the conventions gate scans are recorded for the stop check.
- **At a stop**: `src/__tests__/conventions.test.ts` runs for the files edited in the session, once per checkout, and blocks the stop with the violations; it does not run again while Claude continues because of it.
- **Skills** (`.claude/skills/`): `/gate` runs the exit gate of docs/ROADMAP.md §3 through `node scripts/claude/gate.mjs` (about four minutes; `--only`, `--skip`, `--base`) and reports the first error of each failure and the criteria a script checks (CHANGELOG top section, exceptions without a reason, act() and [WaveUI] warnings, documents changed); `/browser-check <Component>` runs a phase spec's real-browser checklist in Storybook with the Playwright MCP.
- **Agents** (`.claude/agents/`): `wave-conventions-reviewer` reviews a change against the conventions no gate checks; `fluent-parity-researcher` reads Fluent UI v9's source (with `gh`) and docs (context7) and maps the gaps to the ids of docs/research/fluent-ui-v9-comparison.md.
- Claude Code's worktrees live in `.claude/worktrees/`: git ignores them and Vitest excludes them.
