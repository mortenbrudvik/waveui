# Fluent parity, Phase 14: 1.0.0, the API freeze (design)

Date: 2026-11-02. Release: 1.0.0, straight to `latest` (no release candidates). Base: `main` at 0.18.1 (`8f35214`). Branch: `feat/fluent-parity-phase-14`. Roadmap item: `docs/ROADMAP.md`, Phase 14 (P14-01 to P14-06), amended here.

This is the design of the first stable release. The maintainer's instruction was: willing to break anything, all three big breaks in, straight to 1.0.0, decide the rest. Every ruling below is mine and carries what it costs if wrong. Research behind it (read-only, with experiments on the repo's Tailwind 4.3.3): namespaced utilities, the ESM-only work map and the `ref` inventory; their findings are quoted where they decide something.

## 1. Intent

WaveUI 1.0 is a clean break that ends the 0.x compromises:

1. **Nothing of WaveUI's styling can collide with an app's** (P14-01): every class the library draws carries a namespace, in its own cascade layer, and its tokens are offered to apps under a namespace too.
2. **`ref` reaches the element a user focuses** on every form control (reverses 0.18's "keep", P14-04), with `slotProps.root` for the wrapper.
3. **The package is ES modules only** (new): `dist/*.mjs` and `index.d.ts`.
4. **Everything 0.x deprecated is removed** (P14-02), and the three small meaning/type changes land: `Image.alt` required (P14-03), Badge `important` is the neutral high-emphasis badge (P14-05), TimePicker `format` follows the locale (P14-06).
5. **The API is frozen**: semver from 1.0.0, "Upgrading to 1.0" complete, a migration codemod for the utilities.

### Non-goals

- New components or features. Phase 14 adds none (the `slotProps.root` parts and the migration codemod are consequences, not features).
- `WaveProvider classNames` (deferred past 1.0, Phase 13 R17) stays deferred.
- A release-candidate series or a 0.19 bridge release (ruled out by the maintainer).
- Re-deciding the Phase 13 mechanisms (`slotProps`, render-function slot children, Field function child, context hooks): they are the 1.0 surface as released in 0.18.

### Anti-goals (a 1.0 that technically works but fails)

- A prefixed sheet that renders a component differently in any of the three engines.
- A consumer that must configure Wave's internals to avoid collisions.
- Silent breakage: every removed or moved API must fail loudly (a type error or a missing export), never behave differently without a message. The exceptions are documented in the CHANGELOG and the guide: the visual `important` badge, TeachingPopover's Done and the TimePicker default (default changes), a `ref` that moves for an untyped or callback ref (R5), the styling changes listed in R6, the handlers of a dismiss slot object (ruling AZ) and an override of a 0.4 ramp name (ruling BE).

## 2. Rulings

**R1. Straight to 1.0.0; the "announce first" rule is waived for four breaks.** The roadmap's Phase 14 entry says 1.0 changes nothing that a 0.x release did not announce. The maintainer chose three breaks 0.18 never announced (namespaced utilities, `ref` placement, ESM-only) and chose no 0.19; a fourth joined them during the build (amended by Task 25): ruling BE removed the 0.4 ramp names `--brand-N` and `--grey-N` as fallbacks of the `--wave-*` ramps, so an app's override of one stops applying without a message (0.18 announced the removal of `legacy-tokens.css`, not of these reads; the CHANGELOG and UPGRADING name it). The rule stands for everything else (P14-02 to P14-06 were all announced in 0.18). *Cost if wrong:* users of those four get no deprecation period; the CHANGELOG, the "Upgrading to 1.0" guide and the codemod are the substitute.

**R2. The deprecation inventory drives P14-02, then retires.** `src/lib/deprecations.ts` (84 rows: 61 `removed`, 4 `default-changes`, 18 `required`, 1 `decided`) is the binding list of what 1.0 does. While the phase runs, `src/__tests__/deprecations.test.tsx` must stay green at every commit: Task B gives each row a `done` flag. A done row has no call site left, its warning case is dropped (a removed prop is passed with `@ts-expect-error`, which proves the type error the anti-goals require), a file it names must not exist any more, and new absence checks cover the entry, the class-name registry and the CSS; the call-site count ignores done rows. The last P14-02 task deletes the file and its test, fixes `integration.test.tsx` (the two references) and `TEST_ONLY_MODULES` of `verify-dist.mjs` and its fixture test, and the CHANGELOG 1.0.0 section restates every row as a "Removed", "Changed" or "Required" line. **`warnDeprecated` and `resolveDeprecatedProp` stay** (C-NAMING needs them for a rename in a 1.x minor); the roadmap's "no callers" holds when the phase ends. Until the inventory retires, a new table in `UPGRADING-TO-1.0.md` must not use the `| Before | After | Announced in | Warns |` header under the four inventory headings. The `decided` row about `ref` is superseded by R5. *Cost if wrong:* a removal missed has no test; mitigated by the row-by-row inversion check before the file is deleted.

**R3. P14-02, P14-03, P14-05, P14-06 are done as announced** (the inventory rows and the 0.18.0 CHANGELOG "Deprecated" list are the spec of each): old names removed; the optional `details` parameter of `onOpenChange`, `onCheckedValuesChange` and `onCheckedItemsChange` becomes required where it exists; `Image.alt: string` required (`StrictImageProps` stays as the alias 0.18 announced; only the optional `alt` is removed; the development warning for a missing `alt` stays for JavaScript callers, worded without "in 1.0"); Badge and CounterBadge `color="important"` renders Fluent's neutral high-emphasis look (`severe` keeps its orange); TimePicker `format` defaults from the locale's hour cycle (an explicit `format` still wins; no `hourCycle` prop, and TimePicker has no `locale` prop: the server render and the render that hydrates it use `'12h'`, after mount the default follows the browser's language, and a picker mounted in the browser without server HTML follows it from its first render (ruling BD, amended by Task 25: "the first client render" read literally would add a render to every client mount); the guide tells SSR apps to pass `format` for a stable output); `useRovingTabIndex`'s positional form and DataGrid's positional `onSortChange` are removed; the `[presence=` className rule that turns a component's default motion off is removed (a `motion` slot value replaces it). *Cost if wrong:* a row misread; each task's reviewer checks its rows against the inventory.

**R4. ESM-only.**
- Output: ES modules only. `package.json`: `exports["."]` is `{ "types": "./dist/index.d.ts", "default": "./dist/index.mjs" }`; `main` is `./dist/index.mjs`; `module` is dropped; the top-level `types` stays (keeps `moduleResolution: node10` type-checking); `sideEffects` unchanged. `dist/index.cjs`, `index.d.cts`, every `.cjs` and `.cjs.map` are gone (dist unpacked size roughly halves).
- Keep the `.mjs` extension (the exports map has no deep JS subpaths; renaming to `.js` touches ~700 literals for no consumer benefit).
- `vite.config.ts`: a single ES output with `lib.formats: ['es']` (Vite 8 otherwise defaults to `['es','umd']`), `copyIndexDtsToDcts` removed. `check:package` uses attw's `--profile esm-only` (`node16` and `strict` fail an ESM-only package by design); publint stays.
- `scripts/verify-dist.mjs`: the CJS checks go (`checkCjsParity`, the CJS probes, `SERVER_SAFE_MODULES`' `.cjs` entries, the `d.cts` declaration check); new `checkRequireEsm` (the entry loads with `require()` on the Node floor and exposes the same names as `import()`: guards against a future top-level await); a guard fails when `dist` holds any `.cjs` or `.d.cts`.
- `scripts/pack-smoke.mjs` and the fixtures: `smoke.cjs` stays as the `require(esm)` consumer; the type fixtures check `.mts` under `node16` and `.cts` under `node20`.
- `lib/globalRegistry` **stays**: no registry entry exists only for CJS-vs-ESM. Each still guards against two ESM copies (duplicate installs, bundler duplicates, hot reload). Only the rationale comments change.
- Node floor stays `>=22.12.0` (`require(esm)`; 22.12.x prints an ExperimentalWarning, 22.13+ is silent).
- Consumer migration text (for the guide): ES modules only; `require()` works on Node 22.12+ and returns the same module as `import`; TypeScript CommonJS files need `module: node20` or `nodenext` (`node16` reports TS1479); Jest in CommonJS mode must transform the package, use its ESM mode, or move to Vitest.
*Cost if wrong:* CJS-only consumers (Jest CJS, old toolchains) break; the guide says how to migrate.

**R5. `ref` reaches the focusable element (supersedes Phase 13 R19).**
- Rule: for a form control or composite whose root is a wrapper around one focusable element, `ref` reaches that element; `className`, `style` and the rest stay on the root; the wrapper's ref is `slotProps.root.ref`.
- **Moves (12):** Checkbox, Switch, SearchBox, SpinButton, Combobox, Dropdown, TimePicker, DatePicker, TagPicker, ColorSlider, AlphaSlider, `ColorPicker.HexField`.
- **Already there:** Input (and its `slotProps.root`), RadioGroup.Item (gains `slotProps.root`, since no ref reaches its `<label>` today), Textarea, Select, Slider, Listbox, swatches.
- **Stays on the container (not form controls with one focus target):** ColorArea (two inputs, one Tab stop), `Table.SelectionCell`, `DataGrid.SelectionCell`, InfoLabel, and every group/collection root (RadioGroup, Rating, SwatchPicker, ColorPicker, Calendar, Tree, FlatTree, List, Nav, TabList, Toolbar, Menu, SplitButton, TagGroup, InteractionTag, Tag, Card, AvatarGroup, Breadcrumb, Pagination, Accordion, Carousel, the table header cells).
- `controlRef` is **removed** from the 12 movers (TypeScript's excess-property and ref-type errors flag every use); it stays on ColorArea, `Table.SelectionCell` and `DataGrid.SelectionCell`.
- Every mover (and RadioGroup.Item) gains a `root` part: `slotProps.root` as Input's (Phase 13 R6): its classes, style, attributes and handlers merge after the component's; the enumerated `data-*` attributes and `hidden` are locked, `inert` and `aria-hidden` unset; a click is blocked while disabled where the root activates the control (Checkbox, Switch, RadioGroup.Item). `SLOT_PROPS_ROOT_OWNERS` becomes a rule ("components whose `ref` reaches a focusable element inside their root") and lists 14 components (Input, the 12 movers and RadioGroup.Item); each D group adds its owners (the ownership type test forces an owner to declare `root`, so they cannot be listed earlier), and `slotParts.test.ts` replaces Switch as its negative example. Rating.Item (two half-star buttons) is on the "stays" list.
- TagPicker's `ref` follows the trigger that renders (`Ref<HTMLInputElement | HTMLButtonElement>`), covering the built-in form and the parts form; its context field `controlRef` is renamed internally (`controlElementRef`) to end the name clash with the removed prop.
- Test infrastructure: `testSystemProps` gains a `ref: 'control'` option and `ControlQuery.tag` (`ref.current` must equal `getByRole(control.role)`; `expectedTag` keeps meaning the root's tag); a `testRootPartRef` helper checks that `slotProps.root.ref` reaches the `data-testid` element.
- Order: the E rows of a mover (the 0.5 `onChange`/`onOptionSelect` renames, SearchBox `dismiss`) land before that mover's D group, since both edit the same files: D and E run serially.
- Behaviour that changes with no code change and is documented (and integration-tested): `Overflow.Item asChild` measures through a mover child's `ref` (now its control); `Presence` reading animations through `ref`; Tooltip, Popover and Menu triggers anchor to the control (their state ARIA and focus target already resolved to it). Amended by Task 25 from Task 17's integration: Tooltip anchors to its own wrapper `<span>`, so nothing moves for it; Popover and Menu triggers position, return focus and dismiss against the control, while their state ARIA (`aria-expanded`, `aria-haspopup`, `aria-controls`) stays on the root as in 0.18 (where a `<label>` or `<div>` cannot carry it, so a mover is no click-trigger child; a context Menu is the composition to use), and a press on a label root's text is outside the trigger; `Overflow.Item asChild` needed one store change (ruling BH: a hidden item's last size is kept while an element around the measured one carries the marker), and still counts the control's width, not the component's; `Presence` puts its attributes on the root and waits for the control's animations.
*Cost if wrong:* code that holds the wrapper through `ref` (measuring, layout) breaks; `slotProps.root.ref` is the replacement. A mover whose wrapper is intentionally the target (rare) can be reverted per component.

**R6. Namespaced utilities: internals prefixed, tokens offered under `wave`, layers for Tailwind apps.**
- **Internals.** Every utility class a component or `src/lib` recipe writes carries the Tailwind prefix `wave:` (`wave:flex`, `wave:bg-primary`, `wave:not-disabled:not-aria-disabled:hover:bg-primary-hover`, `wave:wave-rtl:-scale-x-100`). `dist/styles.css` is compiled with `prefix(wave)` and an internal, unnamespaced theme file (`src/styles/theme.css`: the `@theme inline reference` mapping `--color-primary: var(--wave-primary)` and the rest, imported only by `scripts/build-css.mjs`), so the sheet emits no theme variables and none of the self-referencing `--wave-shadow-N` that the prefix `wave` would otherwise produce. The spike (§6, Task 1) found `reference` safe, so the prefix is `wave` (not `wv`); the keyframes may stay inside the `reference` block (they are still emitted when an `animate-wave-*` utility uses them). Unprefixed words never generate, so the `@source not inline` list has no work left in the prefixed build (Task 22 removed it); the compile check below has its own allowlist, for the literals its class-context tracing does not reach (tier 2; amended by Task 1, wording by Task 25).
- **`./styles` stays unlayered** (the plain-stylesheet audience, apps without Tailwind): with the prefix the name collisions are gone, and an unlayered sheet keeps 0.18's robustness against an app's unlayered reset (`*{margin:0}`, normalize, Bootstrap reboot), which a layered sheet would lose. `./preflight.css` stays unlayered too (its universal rules lose to single-class utilities, as today).
- **`./tailwind` layers it.** The entry declares `@layer theme, base, components, utilities;`, imports `./tokens.css` with `layer(theme)` (the token rules and the namespaced theme, below), `./base.css` with `layer(base)` (as 0.18 did), and the precompiled utilities alone, `dist/components.css` (the `./styles` build without `tokens.css` and `base.css`; an internal file that only this entry imports, not an export), with `layer(components)`, so in a Tailwind app any of the app's utilities and the app's own unlayered CSS win over Wave in either import order. Across layers specificity no longer matters. (Amended by Task 1 and its fix round: importing the whole `./styles` sheet into `components` would put the token rules there too, so an app's token override in `@layer base` or `@layer theme`, which 0.18 honoured, would lose; a sheet without the tokens but with `base.css` would put Wave's scoped reset in `components`, where it beats the app's own `@layer base` element styles (`h2`, `ul`, `*`) on the app's elements inside a WaveProvider, which 0.18 kept. Only the utilities-only sheet keeps both, and all three render Wave identically.) The one `!important` Wave has (`[hidden]` in base.css) survives the layer: an important declaration of an earlier layer beats every normal declaration (spike: hidden in every form and engine). The entry also carries the `wave-rtl:` variant and no `@source` of `dist`.
- **Consumer theme keys.** `src/styles/tokens.css` carries the namespaced keys (`--color-wave-*`, `--text-wave-*`, `--shadow-wave-*`, `--font-wave*`, `animate-wave-*`, `duration-wave-*`, `ease-wave-*`, mapped to the `--wave-*` tokens), so an app writes `bg-wave-primary`, `text-wave-body-1`, `shadow-wave-4`; a prefixed app (`prefix(tw)`) writes `tw:bg-wave-primary`. The token rules sit in `@layer theme` and are shipped once (the dist sheet does not repeat them for the `./tailwind` path; `tokens.test.ts`'s pins are rewritten).
- **The custom setup is redefined.** `./tokens` + `./variants` + `@source dist` can no longer style components (an unprefixed app build ignores `wave:` classes, and one build carries one prefix). In 1.0 components always come from `./styles` (or `./tailwind`, which layers it), and `./tokens` plus `./variants` expose the namespaced theme and the `wave-rtl:` variant for the app's own classes. The Tailwind fixture and the README section are rewritten.
- **Tailwind-free token utilities:** `@mortenbrudvik/waveui/utilities.css` (and `./utilities`), unlayered like `./styles` (ruling BL, Task 22 fix round 1: in `@layer utilities` its classes lost to the unlayered base styles of `./styles` inside the root; an app links it after `./styles` and before its own CSS), no variants: bg, text, border, ring, fill, stroke, shadow, font and animate utilities of the namespaced keys (~50 KiB minified, ~6.7 KiB gzip, estimated; measured by Task 20 and after the fix round of Task 22: 889 classes, 62,857 B (61.4 KiB) minified, 6,786 B gzip: the estimate was off, not the list). A build-css entry, listed in attw's `--exclude-entrypoints` and pack-smoke's `EXPORTED_SUBPATHS`.
- **`cn`.** One merge, two names (ruling BK, Task 22 fix round 1, which replaced the two configurations planned here and ruling BI's namespaced-only public `cn`): the **public** `cn` calls `wcn`, so the public recipes' prefixed classes (`focusRing`) merge with an app's unprefixed ones, and an app's `cn('p-4','p-2')` merges as before. The **module-only** `wcn` (what components, `lib/slot`, `lib/mergeProps`, `mergeSlotProps` and the hooks that merge recipes call) is tailwind-merge with `prefix: 'wave'` and an `experimentalParseClassName` that parses an unprefixed class as if it carried the prefix (`parseClassName(className.startsWith('wave:') ? className : 'wave:' + className)`, which merges exactly as stripping `wave:` does), so a consumer's unprefixed `p-2` still replaces Wave's `wave:p-4` exactly as in 0.18 (the cascade layer is the second line of defence, not the first). `wcn` knows both the internal scales (`text-body-1`, `shadow-4`) and the namespaced ones (`text-wave-body-1`, `shadow-wave-4`): otherwise a consumer's `text-wave-body-2` reads as a text colour and removes Wave's `wave:text-foreground`. The one `extendTailwindMerge` call is `/* @__PURE__ */`. `tailwind-merge` is pinned to an exact version and a test fails if the parse changes. The `conflictingClass` contract of `testSystemProps` is unchanged.
- **Migration.** `codemod/migrate-1.0.mjs`, shipped in the package (`files`; dependency-free: Node `fs` and regexes; run as `node node_modules/@mortenbrudvik/waveui/codemod/migrate-1.0.mjs <globs>`; added to the lint, format and test globs; allowed by pack-smoke's no-scripts rule), rewrites an app's own classes, `@apply` lines and `var(--color-*)` uses that named Wave's former unprefixed token utilities (`bg-primary`, `text-foreground`, `border-border`, `text-body-1`, `shadow-4`, ...) to the namespaced ones, from the list of Wave's theme keys; the 17 names shared with shadcn (`bg-primary`, `border-border`, `ring-ring`, ...) are rewritten only with `--include-shared`. "Upgrading to 1.0" carries the same table. The stories of this repository are migrated with it (which tests it), and so are the token classes a test passes in as a consumer would; Wave's own classes in the tests go through the test-migration tool (Transition, below).
- **What stays shared or changes, listed as anti-goal exceptions:** Tailwind's `--tw-*` custom properties (version skew between two Tailwind builds); an unlayered reset still beats the layered `./tailwind` form (use `./styles` unlayered, or put the reset in a layer); renamed theme keys; the generic utilities (`flex`, `p-4`) the precompiled sheet used to supply to an app that never defined them; in a Tailwind app an app's bare `bg-*` now also overrides Wave's hover, selected and disabled backgrounds (layer order); an app's own `@layer components` class on a Wave component now competes with Wave's utilities by source order (spike: an app `.app-btn` declared after Wave won; in 0.18 Wave's utilities, in `utilities`, always won); `@keyframes wave-*` appears twice in a Tailwind app's CSS (Wave's sheet and the namespaced theme; identical, harmless); an app's own `@layer base` rules, a `*` rule included, compete with Wave's scoped reset by source order inside the `base` layer, as in 0.18.
- **Transition (the flip is atomic).** The prefix applies to a whole Tailwind build and to the whole merge function, so the repository cannot be half converted. Package F lands in two steps that are each green: **F1** adds everything that works with the prefix off (the `theme.css` split, `wcn` with a configurable prefix, the migration codemod, the compile check, the namespaced keys in `tokens.css`, `utilities.css`, the `./tailwind` and fixtures rewrite behind the prefix constant) and **F2** is one commit that sets the prefix and runs the AST codemod over `src/components`, `src/lib` and `src/hooks`, the test-migration tool over the tests, and `migrate-1.0` over the stories, re-sets the budgets from measurement (R7) and passes every gate. The tests are not a side note (fix round 1 of Task 1 measured them): 228 of the 292 test files hold utility literals, about 5,800 literals that name a class (3,156 `toHaveClass` arguments, about 370 `className` props, 86 `conflictingClass.overrides`, the rest in `it.each` tables, `join`s, `toEqual`/`toContain`/`arrayContaining` and selectors). F1 therefore adds `scripts/prefix-tests-codemod.mjs` (Task 21): it classifies each literal (Wave's own class: prefixed; a consumer class the test passes in, the `className` of a render or `conflictingClass.className`: not; a `querySelector`/`closest`/`matches` selector `.x`: the escaped `.wave\:x`), is idempotent, and its `--report` lists every literal it could not classify for a manual decision (estimated at a few hundred of the roughly 1,700 literals outside the direct contexts, once the tool traces `it.each` rows and helper arguments into `toHaveClass` as the `src` codemod traces into `wcn`). F2 is reviewed by its checks plus samples, not by reading the 4,348 words of `src` and the test literals.
- **Compile check (replaces a conventions-gate rule).** The conventions gate reads every string word as a class token and cannot tell `'fixed'` (a positioning strategy) from a class. At the flip `scripts/build-css.mjs` runs the codemod's `--check`, which reads the string literals of `src/components` and `src/lib` (the TypeScript AST, as `classStringTokens` already does; never Tailwind's scanner, which also reads comments: 67 false alarms in the spike) and tests each word against the unprefixed design system (`candidatesToCss`, plus the `group`/`peer` markers), in two tiers (amended by Task 1 and its fix round). (1) A literal the codemod's class-context tracing reaches (`cn`/`wcn`/`clsx` arguments, `className=`, recipe and `*Classes` maps, `withPartClass`, `lib/styles.ts`, `lib/motion.ts`) fails on any unprefixed utility word, with no allowlist: an unprefixed `relative` in a class string fails even in a file whose style object says `position: 'relative'`. (2) Any other literal (a positioning strategy, an ARIA role, a prop value, an event name, prose) may hold an unprefixed utility word only where the allowlist names that word for that file: a JSON map of file to words, 118 word-file pairs over 22 words in the spike (`absolute blur border collapse container filter fixed grid group hidden inline list-item outline relative resize ring rounded select-all static table underline visible`), never a global word list and not today's `@source not inline` list. Both tiers proved by mutation in the spike: an unprefixed `relative` added to Portal's `wcn` call fails tier 1, a new `'fixed'` in Link fails tier 2.
- **The src codemod is AST-based**, limited to class contexts (`cn`/`wcn`/`clsx` arguments, `className=`, recipe and `*Classes` maps, `withPartClass`, `src/lib/styles.ts`, `src/lib/motion.ts`), with the compile check as its safety net. It also renames `cn` to `wcn` in `src/hooks` (`useCollapsePresence` merges the motion recipes), prefixes the `group`/`peer` markers (`wave:group/row`), and is followed by `prettier --write` (61 files rewrap). The spike's tool is the one Task 21 moves to `scripts/prefix-codemod.mjs`.
- **Task order.** A spike first (below), then F1 after D and E (fewer conflicts), then F2.
*Cost if wrong:* an XL change that fails the spike is abandoned in favour of the runner-up (theme-key namespacing plus a layered sheet, M/L), at the price of the spike only. If it succeeds, apps pay a one-time migration, and a plain-CSS app whose own class competes with a Wave class by order (not by `cn`) may see a different winner than in 0.18.

**R7. Sizes and budgets.** F2 re-sets every budget from measurement and nothing earlier than F2 touches them: `RECORDED_IMPORTS_0_18` (with the 0.17 budgets it carries for the brand, token, presence and virtual-window probes, `DATA_GRID_BUDGET`, `PRESENCE_BUDGET` and `VIRTUAL_BUDGET`) fold into one `RECORDED_IMPORTS_1_0`, each budget its measured size at F2 plus 512 B minified and 192 B gzip, recorded against a new `BASELINES_0_18_1` (the 0.18.1 measurements) with the growth in the CHANGELOG; the growth of `dist/styles.css` (about 6 bytes per selector) is recorded without a budget. Packages D and E run under the 0.18 budgets; if D's `root` parts exceed a margin the task adds a small, explicit interim allowance as Phase 13 did. The prefix lengthens class strings (about 5 bytes per class word in the minified JS; gzip absorbs most); the removed aliases shrink them. ESM-only changes no import's size. *Cost if wrong:* a budget set too loose hides a later regression; too tight forces a re-base in 1.0.x.

**R8. The release.** `package.json` 1.0.0, CHANGELOG `## [1.0.0]`, ROADMAP status, "Upgrading to 1.0" final, then merge, tag `v1.0.0` and the release workflow publish to `latest`. **Merge, push, tag and publish need the maintainer's explicit go-ahead at that point**: an irreversible release is not covered by "decide the rest".

**R9. Semver commitment.** From 1.0.0 the public API is the entry's exports, the class-name registry (`wave-*` stable classes), the `--wave-*` tokens, the namespaced theme keys, the CSS entries and the documented props; the internals listed as module-only are not. CLAUDE.md states it.

### Rulings made during the build (AZ to BL)

The controller's rulings on what the tasks found, letter-numbered after Phase 13's (A to AY); each is described where it was made in §6, with what it costs if wrong. Collected here by Task 25.

- **AZ (Task 8), the dismiss slots' object forms.** In MessageBar `dismiss`, SearchBox `dismiss` and Tag `dismissIcon` (now `Slot<'span'>`), a `<button>`/`Button` element is still merged into the built-in button; any other slot object is the content element (its attributes, `className`, `style`, `ref` and handlers stay on it, only its naming attributes reach the button); an object whose `as` is `'button'` or `Button` is unwrapped like the glyph slots (children render, props dropped) with a development warning (`MessageBar:dismiss-button-slot-object`, `SearchBox:dismiss-button-slot-object`, `Tag:dismissIcon-button-slot-object`, no "in 1.0"). The close slots (`closeButton`, `dismissButton`) are unchanged. *Cost if wrong:* a `{ as: 'button', onClick }` user loses the handler (the warning says why), and a TypeScript user's `dismiss={{ onClick }}` compiles and lands on the content span (UPGRADING says so).
- **BA (Task 8), PresenceBadge `'dnd'` and `'oof'`.** Untyped code passing them throws a `TypeError` during render, as any unknown status did in 0.18; no fallback, no warning. *Cost if wrong:* a page crash on legacy server data instead of a degraded badge. **Open: a decision for the maintainer** (keep the throw, or add a fallback with a development warning; §6, Task 25, known limits).
- **BB (Task 9), DataGrid's `onSortChange` without `items`, `sort` or `defaultSort`.** That union member declares `onSortChange?: never`, so every 0.x positional use fails loudly, an unannotated `(columnId, direction) => …` included; `defaultSort={null}` hears an uncontrolled grid. *Cost if wrong:* one member's type; allowing the object form there later is a widening a 1.x minor can make.
- **BC (Task 10), `TableResizeHandleBindings.onResize(width, details?)`.** It stays optional: an input that a handle (or a consumer's own handle) calls, with no inventory row; it still fits the handle's now-required `onResize`. *Cost if wrong:* one line.
